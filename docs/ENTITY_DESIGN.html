2 · Entity reference

EntityResponsibilityKey design points
UserPlatform membercohort drives cohort-based eligibility; email unique.
MembershipPlanBilling cadence + priceBillingCycle enum carries duration months → expiry math. One plan per cycle.
MembershipTierA tier & its perks/gatesrank orders tiers for upgrade/downgrade; baseTier = default. Owns benefits + rules (cascade).
TierBenefitOne configurable perkStored as rows (not flags) → add/remove/retune perks at runtime.
TierEligibilityRuleOne promotion criterionMaps to a Strategy by type; ALL rules of a tier must pass.
SubscriptionUser↔Plan↔Tier for a window@Version optimistic lock; unique idempotencyKey; lazy expiry.
OrderA purchaseRaw signal for order-count & monthly-spend rules.

3 · Design rationale (abstractions, extensibility, modularity)

DecisionWhy
Benefits & rules as child rows, not boolean columnsNew perks/criteria need no schema or code change — the program is configured as data and editable via APIs.
Plan and Tier are separate entitiesOrthogonal concerns: billing cadence vs. benefit level. A user keeps their plan while moving tiers.
Enums for cycle / benefit / rule / statusType-safety + each enum constant pairs with a strategy or duration, keeping behaviour close to data.
tier_rank as an integerSingle source of truth for ordering → trivial, correct upgrade/downgrade comparisons.
Version + idempotency on SubscriptionConcurrency-safe lifecycle without pessimistic DB locks (see Architecture §5).
Reserved words mapped (tier_rank, benefit_value)Portable across H2 / other SQL engines.
