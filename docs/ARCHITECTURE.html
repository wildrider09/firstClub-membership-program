1 · Component architecture

Classic layered architecture. Each layer depends only on the one below it; the tier eligibility engine is an isolated, pluggable module.

3 · Subscribe & tier-promotion flow

Subscribing with no tier auto-assigns the highest tier the user qualifies for. Upgrades enforce eligibility.

4 · Extensible tier engine (Strategy + Open/Closed)

Tier promotion is data-driven, not hard-coded. Each criterion is its own strategy bean.

  • TierEligibilityStrategy — interface with supportedType() + isSatisfied(rule, snapshot).
  • Implementations: MinOrderCountStrategy, MinMonthlyOrderValueStrategy, RequiredCohortStrategy.
  • TierEligibilityEvaluator injects all strategies into an EnumMap and applies a tier's rules with AND semantics.
  • Adding a new criterion = add an EligibilityRuleType + one bean. No existing class changes (Open/Closed).
  • Configurable at runtime: benefits (TierBenefit) and rules (TierEligibilityRule) are rows, editable via admin APIs.
flowchart LR R["Tier rules\n(data rows)"] --> EV[TierEligibilityEvaluator] SNAP["UserActivitySnapshot\norders · spend · cohort"] --> EV EV --> M{{"EnumMap<RuleType, Strategy>"}} M --> S1[MinOrderCount] M --> S2[MinMonthlyOrderValue] M --> S3[RequiredCohort] M --> S4["+ future strategy\n(add-only)"] S1 & S2 & S3 --> AND["ALL rules pass?\n(AND)"] --> RESULT["qualifies / highest tier"]

5 · Concurrency approach & design

The bonus ask. Concurrent mutations on the same subscription must never silently clobber each other.

MechanismWhereProtects against
Optimistic locking (@Version)Subscription.versionLost updates from concurrent upgrade/downgrade/cancel
